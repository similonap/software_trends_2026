Deel 2 — Hoe npm werkt · 0:05–0:12

Een binding.gyp is het bouwrecept van een native addon: een module in C of C++ die Node.js laadt alsof het JavaScript is. Normaal gebruik. Sommige taken kan JavaScript niet, of niet snel genoeg: bestandswijzigingen volgen via FSEvents (macOS) of inotify (Linux), een C-bibliotheek zoals SQLite of LMDB gebruiken, zwaar rekenwerk. Het package bevat C/C++-broncode en een binding.gyp. node-gyp vertaalt dat recept naar een Makefile, Xcode- of Visual Studio-project en compileert met de compiler op jouw machine, tot een .node-bestand dat je met require() laadt. Daarvoor zijn Python, make en een C/C++-compiler nodig; daarom faalt npm install soms met een lange node-gyp-foutmelding. Waarom tijdens de installatie? Machinecode hangt af van besturingssysteem, processor (x64, arm64) en soms de C-bibliotheek (glibc, musl). Node-API houdt een addon stabiel over Node.js-versies heen, maar niet over platformen. Het onzichtbare script: staat er een binding.gyp in de root en heeft het package geen eigen install- of preinstall-script, dan voert npm zelf node-gyp rebuild uit. Een maintainer zet dat uit met "gypfile": false. Het risico: GYP voert alles tussen <!( en ) uit via de shell, nog voor er gecompileerd wordt. In dit echte voorbeeld start dat node -p om een pad op te vragen, wat volkomen normaal is. Maar een kwaadaardig binding.gyp kan daar elk commando zetten, en wie alleen naar scripts in package.json kijkt, ziet niets (Phantom Gyp, 2026). Vandaag de norm: @parcel/watcher, lmdb en msgpackr-extract publiceren per platform een voorgecompileerde binary als optionele dependency, zoals @parcel/watcher-linux-x64-glibc. Hun install script compileert alleen als terugvaloptie. Daarom werken ze op een gewoon platform vaak ook als npm 12 het script overslaat; test dat voor je goedkeurt.
