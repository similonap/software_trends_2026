Komt het token van release.yml in jouw repository? Dan eenmalig publicatierecht, plus provenance.

Algemeen beschikbaar sinds 31 juli 2025 voor GitHub Actions en GitLab.com, CircleCI sinds april 2026. Vereist npm 11.5.1+ en een gehoste runner.

Daarna: verwijder alle oude tokens en kies disallow tokens. Eén vergeten token naast trusted publishing volstaat (axios).

Staged publishing (sinds 22 mei 2026): CI zet de versie klaar, een maintainer keurt goed met 2FA.

Deel 6 — Verdediging als maintainer en in CI/CD · 0:36–0:40

Met trusted publishing bewaar je geen npm-token meer in je CI. De pipeline vraagt aan GitHub een kortlevend OIDC-token dat zegt “ik ben workflow release.yml in repository X”. npm controleert dat tegen de configuratie van je package en geeft eenmalig publicatierecht. Er is niets dat langer leeft dan één job, en dus niets dat een worm kan meenemen. Maar binnen die ene job is het token wel bruikbaar: zie TanStack, waar aanvallerscode het uit het geheugen van de runner las. Daarom bestaat de workflow bewust uit twee jobs. De build-job voert de code van je dependencies en je tests uit, maar kan geen OIDC-token vragen. De publish-job krijgt alleen de gebouwde tarball, voert geen vreemde code uit, en draait in een environment met een verplichte reviewer. De volledige release.yml staat in de cursustekst. Praktisch: npm 11.5.1 of hoger in de publish-job, alleen door het platform gehoste runners, en met npm trust (sinds npm 11.10) stel je het vanaf de opdrachtregel in. Staged publishing (verdieping): CI voert npm stage publish uit, en de versie wordt pas installeerbaar nadat een maintainer ze met 2FA goedkeurt. Vanaf ongeveer januari 2027 kunnen tokens die 2FA omzeilen alleen nog stagen, niet meer rechtstreeks publiceren. Oefening 4 laat studenten dit zelf opzetten met een scoped testpackage.
