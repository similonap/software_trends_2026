De lockfile bevriest vertrouwen

"node_modules/debug": {
  "version": "4.4.3",
  "resolved": "https://registry.npmjs.org/debug/-/debug-4.4.3.tgz",
  "integrity": "sha512-RGwwWnwQvkVfavKVt22FGLw+xYSdzARwm0ru6DhTVA3u…",
  "dependencies": { "ms": "^2.1.3" }
}

npm install

respecteert de lockfile, maar mag ze bijwerken als package.json iets anders vraagt

npm ci

installeert exact de lockfile en faalt bij een verschil. Gebruik dit in CI en bij deployments.

Wat ze niet doet

Een kwaadaardige versie die al in de lockfile zat toen je ze maakte, blijft gewoon staan.

Deel 2 — Hoe npm werkt · 0:05–0:12

Bij de eerste installatie schrijft npm package-lock.json. Die legt per package de exacte versie, de bron-URL (resolved) en een integrity-hash vast. Dit is de echte entry voor debug in het express-project van de demo; de integrity-waarde is hier ingekort. De integrity-waarde is een SHA-512-hash van de tarball. Bij een volgende installatie controleert npm dat de gedownloade bytes exact overeenkomen. npm install respecteert de lockfile, maar mag ze bijwerken. npm ci installeert exact wat in de lockfile staat, verwijdert eerst node_modules en faalt als package.json en lockfile niet overeenkomen. Belangrijk: een lockfile beschermt tegen wijzigingen ná het moment van locken. Ze beschermt niet tegen een kwaadaardige versie die al in je lockfile zat. De lockfile bevriest je vertrouwen; ze creëert het niet. Sinds 2016 is een gepubliceerde versie op npm bovendien onveranderlijk: hetzelfde versienummer kan nooit opnieuw met andere inhoud verschijnen. Daardoor zijn installaties vanuit een lockfile reproduceerbaar.
