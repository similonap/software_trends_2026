Voorbeeld: de lijst [Melk, Brood] wordt [Kaas, Melk, Brood], er komt een item vooraan bij.

Kernbegrip

21

Regel drie, de kinderen, verdient een eigen slide, want hier gaan in de praktijk veel dingen mis. Neem een lijst met twee items, Melk en Brood. We voegen vooraan Kaas toe. Hoe vergelijkt React de oude en de nieuwe kinderen? Links: zonder key. React vergelijkt de kinderen op positie. Op positie nul stond Melk, nu staat er Kaas: zelfde type li, dus volgens regel twee wordt de tekst aangepast. Op positie één stond Brood, nu Melk: weer de tekst aanpassen. Op positie twee stond niets, nu Brood: een nieuw li-element maken. Drie DOM-operaties voor wat eigenlijk één invoeging is. Bij een lijst van duizend items worden het er duizend en één. Erger nog: als die items state hebben, bijvoorbeeld een aangevinkt vakje of een half ingevuld invoerveld, dan blijft die state aan de positie hangen. Had je Melk aangevinkt, dan is na de invoeging plots Kaas aangevinkt. Rechts: met key. Elk item krijgt een unieke key. Nu koppelt React de kinderen op basis van hun key in plaats van hun positie. De keys m en b bestonden al: die elementen blijven gewoon staan. Key k is nieuw: één li invoegen. Eén DOM-operatie, en de state blijft bij het juiste item. In code geef je de key mee in de map-functie, zoals onderaan. Twee regels voor een goede key. Hij moet uniek zijn binnen de lijst, en stabiel: hetzelfde item heeft bij elke render dezelfde key. Een id uit de database is ideaal. Gebruik niet de index uit de map-functie als key, tenzij de lijst nooit verandert: de index verschuift bij invoegen, verwijderen of sorteren, en dan heb je exact hetzelfde probleem als zonder key. React toont trouwens een waarschuwing in de console als je de key vergeet. Samengevat: de key helpt het reconciliation-algoritme om te herkennen welk element welk is.
