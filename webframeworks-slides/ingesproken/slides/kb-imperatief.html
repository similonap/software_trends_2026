Imperatief vs declaratief

Imperatief (vanilla JS): jij zegt hoe de DOM moet veranderen

let count = 0;
const btn = document.querySelector('#btn');
btn.addEventListener('click', () => {
  count++;
  btn.textContent = count;
  if (count > 5) btn.classList.add('rood');
});

Elke toestandsovergang programmeer je zelf. Vergeet je er één, dan klopt het scherm niet meer met de data.

Declaratief (React): jij zegt wat er moet staan

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button
      className={count > 5 ? 'rood' : ''}
      onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}

UI = f(state): het framework zoekt zelf uit welke DOM-aanpassingen nodig zijn.

Kernbegrip

15

Waarom gebruiken we eigenlijk frameworks om de DOM aan te passen? Het antwoord zit in het verschil tussen imperatief en declaratief programmeren. Links staat imperatieve code, in gewone JavaScript zonder framework. Imperatief betekent: je geeft stap voor stap opdrachten over hoe iets moet gebeuren. We houden een teller bij, zoeken de knop op, en bij elke klik verhogen we de teller, passen we de tekst van de knop aan, en als de teller boven vijf komt, voegen we een CSS-klasse toe. Voor één knop is dat prima. Maar in een echte applicatie met honderden elementen en tientallen soorten acties moet je voor elke mogelijke overgang zelf programmeren wat er in de DOM verandert. Wat als de teller weer onder vijf zakt? Dan moet je de klasse ook weer verwijderen; dat zijn we hier vergeten. Dat is precies het soort bug dat in imperatieve UI-code voortdurend sluipt: de data en het scherm raken uit sync. Rechts staat declaratieve code in React. Declaratief betekent: je beschrijft wat het resultaat moet zijn, niet hoe je er komt. De functie Counter zegt: voor een gegeven waarde van count ziet de knop er zo uit, met die tekst en die klasse. Je beschrijft de UI voor elke mogelijke toestand tegelijk. Als count verandert, roept React de functie opnieuw aan, krijgt een nieuwe beschrijving, en zoekt zelf uit welke DOM-aanpassingen nodig zijn om van de oude naar de nieuwe toestand te gaan. Het probleem van de vergeten klasse kan hier niet bestaan. Dat idee vat je samen als UI is een functie van de state: UI = f(state). Het is het kernidee achter React, Vue, Angular en Svelte. Maar het roept meteen een vraag op: als React bij elke wijziging opnieuw de hele beschrijving maakt, hoe weet het dan welke DOM-aanpassingen echt nodig zijn, zonder telkens de hele DOM opnieuw op te bouwen? Het antwoord is de virtual DOM.
