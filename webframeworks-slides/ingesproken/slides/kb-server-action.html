Een Server Action is een publiek endpoint

'use server';

export async function deletePost(id) {
  // 1. authenticatie: wie ben je?
  const user = await getSession();
  // 2. autorisatie: mag jij dit?
  if (!user?.isAdmin) throw new Error('403');
  // 3. validatie: is de input geldig?
  const postId = z.uuid().parse(id);
  await db.post.delete({ where: { id: postId } });
}

Wat er echt gebeurt:

  1. Het framework geeft de functie een ID
  2. De client roept deletePost(5) aan: dat wordt een HTTP POST met het ID en de geserialiseerde argumenten
  3. De server deserialiseert de argumenten en voert de functie uit
  4. Iedereen kan dat request zelf sturen, ook zonder jouw UI

Elke Server Action controleert dus zelf: authenticatie, autorisatie en inputvalidatie.

Een cruciaal inzicht: een Server Action, of een remote function in SvelteKit, is een publiek HTTP-endpoint, ook al ziet het eruit als een gewone functie. Wat gebeurt er als je in Next.js een functie met ‘use server’ markeert? Het framework geeft die functie een uniek ID. Wanneer je in een client component deletePost(5) aanroept, voert de browser niet echt die functie uit. Hij stuurt een HTTP POST-request naar de server, met het ID van de functie en de argumenten, omgezet naar tekst. Dat omzetten heet serialiseren. De server zet de tekst weer om naar JavaScript-waarden, deserialiseren, en voert de functie uit. Waarom is dat belangrijk? Omdat iedereen dat request zelf kan sturen, bijvoorbeeld met curl of een script, zonder ooit jouw knop te gebruiken. Als je de knop ‘verwijder’ alleen toont aan admins, maar in de functie niet controleert wie de aanroep doet, kan elke bezoeker posts verwijderen. Daarom moet elke server action drie controles doen, zoals in de code. Eén: authenticatie, wie ben je? Twee: autorisatie, mag jij dit doen? Drie: validatie, is de input wat we verwachten? Hier gebruiken we de library zod om te controleren dat het ID een geldig UUID is. Vertrouw nooit input van de client, ook niet als je eigen frontend die stuurt. En er is nog een risico, waar je als developer geen controle over hebt: de stap waarin de server de argumenten deserialiseert, gebeurt in het framework zelf, nog voor jouw code draait. Zit daar een fout in, dan helpen jouw controles niet. Dat is precies wat er bij React2Shell gebeurde. Daarvoor moeten we eerst serialisatie begrijpen.
