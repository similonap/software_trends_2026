Next.js 16.3: Instant Navigations

“…the long-standing (and valid!) criticism that Server Components can make apps feel unresponsive.” (Next.js-team, juni 2026)

Wacht een route op data, dan moet de developer kiezen:

  • Stream: <Suspense> rond de data, meteen een laadstatus
  • Cache: 'use cache', meteen een eerder gerenderde versie
  • Block: instant = false, bewust wachten op de server

Partial Prefetching: één herbruikbare shell (het skelet van een pagina) per route prefetchen, in plaats van een request per link.

Dit is een van de meest veelzeggende momenten van het jaar. Bij de aankondiging van Next.js 16.3 schreef het Next.js-team letterlijk over de al lang bestaande, en terechte, kritiek dat Server Components apps traag kunnen laten aanvoelen. Het uitroepteken staat er echt. Het probleem kennen we van het kernbegrip navigatie: in een server-gedreven app klik je, gebeurt er even niets, en verschijnt dan de volgende pagina. In een SPA zie je bij een klik meteen het skelet van de volgende pagina. Dat voelt sneller, ook al duurt het in totaal even lang. Next.js 16.3 lost dit op met Instant Navigations. Als een route op de server op data wacht, krijg je tijdens het ontwikkelen een foutmelding die je verplicht om te kiezen. Stream: je zet de trage data in een Suspense-boundary, zodat de gebruiker meteen een laadstatus ziet. Cache: je markeert de data met ‘use cache’, zodat de gebruiker meteen een eerder gerenderde versie ziet. Of Block: je zegt bewust dat deze navigatie mag wachten, bijvoorbeeld voor een blogpost waar je geen laadscherm wil. Daarnaast veranderde het prefetchen. Vroeger stuurde Next.js voor elke zichtbare link een apart prefetch-request: twintig chatgesprekken in een zijbalk betekende twintig requests. Het team gaf zelf toe dat dat er belachelijk uitzag. Met Partial Prefetching wordt per route één herbruikbare shell opgehaald: het skelet van de pagina, zoals de layout en de laadindicatoren. Die shell wordt voor alle links naar die route hergebruikt, net zoals een SPA de code per route één keer laadt. De les: de slinger zwaait niet gewoon terug naar de client. Frameworks proberen het beste van beide te combineren, maar de prijs is complexiteit: je moet per stukje UI een bewuste keuze maken.
