Van state naar scherm: render en commit

1. Trigger

setCount(1) wordt aangeroepen; React plant een update

2. Render

React roept Counter() opnieuw aan: nieuwe virtuele boom

3. Reconciliation

Nieuwe boom vergelijken met de vorige: lijst van wijzigingen

4. Commit

Enkel die wijzigingen in de echte DOM; browser tekent

  • Renderfase (stap 2 en 3): enkel rekenen in het geheugen, de DOM blijft onaangeroerd. Moet puur zijn. Kan sinds React 16 (Fiber) onderbroken worden voor dringender werk.
  • Commitfase (stap 4): de DOM wordt in één keer aangepast, zonder onderbreking. Daarna draaien de effects (useEffect).
  • Let op: ‘renderen’ betekent in React de componentfunctie uitvoeren, niet ‘pixels tekenen’. Een render zonder verschillen leidt tot nul DOM-aanpassingen.

Kernbegrip

17

Wat gebeurt er nu precies tussen het moment dat je op de knop klikt en het moment dat je het nieuwe getal ziet? React doet dat in vier stappen. Stap één, de trigger. Je event handler roept setCount aan. React voert de update niet onmiddellijk uit, maar plant ze in. Als je in één event handler meerdere keren state aanpast, worden die updates gebundeld tot één render. Dat heet batching. Stap twee, render. React roept de componentfunctie Counter opnieuw aan, nu met de nieuwe waarde van count. De functie geeft nieuwe JSX terug, dus een nieuwe virtuele boom. Belangrijk: in React-terminologie betekent renderen dus ‘de componentfunctie uitvoeren’, en niet ‘pixels op het scherm tekenen’. Dat verwart veel mensen. Stap drie, reconciliation. React vergelijkt de nieuwe virtuele boom met de vorige en maakt een lijst van wat er echt veranderd is. Hoe dat vergelijken werkt, zien we op de volgende slide. Stap vier, commit. React voert enkel die wijzigingen uit op de echte DOM, en daarna tekent de browser het scherm opnieuw. React groepeert dat in twee fases. De renderfase, stap twee en drie, gebeurt volledig in het geheugen: er wordt niets aan de DOM veranderd. Daarom moet die fase puur zijn: je mag tijdens het renderen geen side effects doen zoals data versturen of globale variabelen aanpassen. Sinds React 16 gebruikt React daarvoor een architectuur die Fiber heet: het renderwerk wordt opgesplitst in kleine eenheden, zodat React het kan onderbreken als er iets dringenders gebeurt, zoals de gebruiker die typt. Daar zijn bijvoorbeeld startTransition en useDeferredValue op gebouwd. De commitfase, stap vier, kan niet onderbroken worden: de DOM wordt in één keer aangepast, zodat de gebruiker nooit een half bijgewerkt scherm ziet. Pas daarna draaien de effects, zoals useEffect. En een belangrijk gevolg: als een render exact dezelfde boom oplevert, worden er nul DOM-aanpassingen gedaan. Een render is dus niet automatisch duur, maar te veel onnodige renders van grote componenten wel.
